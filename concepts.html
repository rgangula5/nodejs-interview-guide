1 · Networking & HTTP Fundamentals

HTTP methods & when

GET (read, safe, idempotent), POST (create, not idempotent), PUT (full replace, idempotent), PATCH (partial update), DELETE (idempotent). "Safe" = no side effects; "idempotent" = same result if retried.

Key status codes

2xx success (200, 201 created, 204 no content), 3xx redirect (301/304), 4xx client (400 bad, 401 unauth, 403 forbidden, 404, 409 conflict, 422 validation, 429 too many), 5xx server (500, 502 bad gateway, 503 unavailable, 504 timeout).

HTTP/1.1 vs 2 vs 3

1.1 = one request per connection (head-of-line blocking, keep-alive helps). 2 = multiplexing many streams over one TCP connection, header compression, server push. 3 = runs over QUIC (UDP), removes TCP head-of-line blocking, faster connection setup.

TCP vs UDP

TCP = connection-oriented, reliable, ordered, slower (handshake, retransmit) — used for HTTP/APIs. UDP = connectionless, no guarantees, fast — used for video, DNS, QUIC.

HTTPS / TLS

Encrypts traffic. TLS handshake: client hello → server cert (public key) → key exchange → symmetric session key. Gives confidentiality, integrity, authentication (via CA-signed cert).

DNS

Resolves domain → IP. Recursive resolver → root → TLD → authoritative. Cached with TTL. Round-robin / GeoDNS can do basic load balancing.

REST vs RPC/gRPC vs GraphQL

  • REST — resources + HTTP verbs; simple, cacheable; can over/under-fetch.
  • gRPC — binary (protobuf) over HTTP/2; fast, strongly typed, streaming; great service-to-service; not browser-native.
  • GraphQL — client asks for exactly the fields it needs (one endpoint); solves over/under-fetching; caching & rate-limiting are harder.

WebSockets vs long-polling vs SSE

WebSocket = full-duplex persistent connection (chat, live). SSE = server→client one-way stream over HTTP. Long-polling = client repeatedly holds a request open — fallback when WS unavailable.

2 · API Design

  • Idempotency — retrying must not double-charge; use an idempotency key for POST (client sends a unique key; server dedupes).
  • Versioning — URL (/v1), header, or content negotiation. Never break existing clients.
  • Pagination — offset/limit (simple, slow deep) vs cursor/keyset (scales, stable under inserts).
  • Rate limiting — token bucket / leaky bucket / fixed & sliding window; return 429 + Retry-After.
  • Errors — consistent shape ({code, message}), correct status, no leaking internals.
  • Contracts — validate input at the edge; use OpenAPI/JSON-schema; backward-compatible changes only.
Say this: "For a payments POST I require an idempotency key so a client retry after a network blip doesn't double-charge — the server records the key and returns the original result."

3 · Authentication & Authorization

AuthN = who you are; AuthZ = what you can do.

  • Sessions — server stores state, client holds cookie. Easy revoke; needs shared store to scale.
  • JWT — stateless signed token; scales; hard to revoke (short TTL + refresh). Signed, not encrypted — no secrets inside.
  • OAuth 2.0 — delegated authorization ("Login with Google"); flows: authorization code (web apps), client credentials (service-to-service), PKCE (mobile/SPA).
  • OpenID Connect — identity layer on top of OAuth2 (adds ID token = who the user is).
  • RBAC vs ABAC — roles (admin/user) vs attribute-based policies (dept + resource + action).
  • Service-to-service — API keys, mTLS, or short-lived tokens; least privilege.

4 · Caching

Why & where

Reduce latency & load. Layers: browser → CDN (edge) → API/app cache (Redis/Memcached) → DB cache. Cache what's read-heavy and changes rarely.

Strategies

  • Cache-aside (lazy) — app checks cache, on miss reads DB and populates. Most common.
  • Write-through — write to cache + DB together (consistent, slower writes).
  • Write-back — write to cache, flush to DB later (fast, risk of loss).
  • Write-around — write DB only; cache populated on read.

Eviction & invalidation

Eviction: LRU / LFU / TTL. Invalidation is the hard part ("there are only two hard things..."): use TTLs, versioned keys, or event-based invalidation. Watch for cache stampede (many misses at once) — mitigate with locks / request coalescing / staggered TTLs.

5 · Scalability & Load Balancing

  • Vertical (bigger machine) vs horizontal (more machines). Horizontal scales further; needs stateless services.
  • Stateless services — no in-memory session; store state in Redis/DB so any instance can serve any request (enables scaling + failover).
  • Load balancer — L4 (TCP, fast) vs L7 (HTTP-aware, can route by path/header). Algorithms: round-robin, least-connections, IP-hash, weighted.
  • Sharding/partitioning — split data across nodes by a key (hash or range). Scales writes; adds routing + rebalancing complexity.
  • Replication — copies for read scaling + HA (primary/replica). Watch replication lag / read-after-write consistency.
  • Autoscaling — add/remove instances on CPU/queue-depth/latency.

6 · Distributed Systems

CAP theorem

In a network partition, you must choose Consistency or Availability — can't have both. CP system rejects writes to stay consistent; AP system stays up but may serve stale data. (No partition → you can have both.)

Consistency models

Strong — every read sees the latest write (slower, coordination). Eventual — replicas converge over time (fast, may read stale). Read-your-writes / causal — middle grounds.

Idempotency & exactly-once

Networks retry, so design operations to be safe to repeat. True "exactly-once delivery" is impossible; you get at-least-once delivery + idempotent processing = effectively-once.

Distributed transactions

2PC (two-phase commit) — coordinator prepares then commits; blocking, poor availability. Saga — sequence of local transactions with compensating actions on failure; preferred in microservices.

Consensus

Raft/Paxos — how nodes agree on a value/leader despite failures (used by etcd, Kafka controllers, DBs). At interview level: "leader election + replicated log, majority quorum."

7 · Messaging & Event-Driven

  • Queue (point-to-point) — one consumer processes each message (SQS, RabbitMQ). Pub/Sub — many subscribers get each message (SNS, Kafka topics).
  • Why async messaging — decoupling, buffering spikes, retries, resilience (producer doesn't wait on consumer).
  • Delivery guarantees — at-most-once (may lose), at-least-once (may dup → need idempotency), exactly-once (hard/limited).
  • Ordering — global ordering is expensive; use partitions/FIFO groups for per-key ordering (Kafka partition key, SQS FIFO group).
  • Dead-letter queue (DLQ) — messages that keep failing go here for inspection instead of blocking the queue.
  • Backpressure — slow consumers; handle via queue buffering, rate limits, scaling consumers.
  • Kafka vs SQS/RabbitMQ — Kafka = high-throughput distributed log, replayable, ordered per partition; SQS = simple managed queue; RabbitMQ = flexible routing.
  • Event sourcing / CQRS — store events as source of truth (replayable); separate read & write models.
Say this (your strength): "I built event-driven services on SQS/EventBridge — at-least-once delivery, so I made handlers idempotent with a dedupe key, and pushed poison messages to a DLQ instead of blocking the pipeline."

8 · Microservices & Communication

  • Monolith vs microservices — monolith = simple, one deploy, tight coupling; microservices = independent deploy/scale, but network complexity, distributed data, ops overhead. Start monolith, split when needed.
  • Sync (REST/gRPC) vs async (events/queues) communication — async decouples and adds resilience.
  • Service discovery — how services find each other (DNS, registry like Consul, or platform like k8s Services).
  • API gateway — single entry: routing, auth, rate limiting, aggregation.
  • Data per service — each service owns its data; no shared DB. Cross-service consistency via events/saga.
  • Patterns — circuit breaker, bulkhead, sidecar, strangler fig (incremental migration), BFF (backend-for-frontend).

9 · Reliability & Resilience Patterns

  • Retries with exponential backoff + jitter — avoid retry storms; cap attempts.
  • Timeouts — never wait forever on a downstream call.
  • Circuit breaker — after N failures, "open" the circuit and fail fast for a while, then half-open to test recovery — stops cascading failures.
  • Bulkhead — isolate resources (thread/connection pools) so one failing dependency doesn't sink everything.
  • Idempotency — safe retries.
  • Graceful degradation / fallback — serve cached/partial data when a dependency is down.
  • Rate limiting & load shedding — protect yourself; drop excess load early.
  • Health checks + graceful shutdown — for orchestrators (k8s liveness/readiness).

10 · Concurrency, Throughput & Performance

  • Latency vs throughput — latency = time per request; throughput = requests/sec. Optimize the one that matters.
  • p50/p95/p99 — talk in percentiles, not averages; tail latency matters at scale.
  • Connection pooling — reuse DB/HTTP connections; opening per request is expensive.
  • Async I/O vs threads — async (Node) scales I/O cheaply; threads for CPU work.
  • Batching & N+1 — batch calls, avoid N+1 query patterns.
  • Backpressure — don't accept work faster than you can process.
  • Profiling — measure before optimizing; find the actual bottleneck.

11 · Security (OWASP-level, conceptual)

  • Injection (SQL/command) — use parameterized queries / validation.
  • XSS — escape output, CSP headers.
  • CSRF — tokens / SameSite cookies (for cookie-based auth).
  • SSRF — validate/allowlist outbound URLs.
  • Broken auth/access control — enforce authZ on every request, least privilege.
  • Secrets — in a secret manager/env, never in code; rotate.
  • Encryption — TLS in transit, encryption at rest (KMS).
  • DDoS/abuse — rate limiting, WAF, CDN.
  • Dependencies — scan & patch (supply-chain).

12 · Observability

Three pillars:

  • Logs — structured (JSON), with a correlation/trace ID to follow a request across services.
  • Metrics — numeric time-series (latency, error rate, throughput, saturation — the "RED"/"USE" methods).
  • Traces — distributed tracing shows a request's path & timing across services (OpenTelemetry, Jaeger, Dynatrace).

SLI/SLO/SLA — indicator (measured), objective (target, e.g. 99.9%), agreement (contract). Error budget = allowed unreliability. Alert on symptoms (user-facing), not just causes.

13 · System Design — How to Approach It (verbal)

Even for non-coding rounds, they'll say "how would you design X." Use this order out loud:

  1. Clarify requirements — functional + non-functional (scale, latency, consistency, read/write ratio).
  2. Estimate scale — users, QPS, data size (rough numbers show seniority).
  3. Define the API — a few key endpoints.
  4. High-level design — client → LB → services → cache → data store → queue. Draw the boxes.
  5. Data model — key entities & access patterns (keep light if DB-excluded).
  6. Deep-dive — pick 1–2 hard parts (caching, sharding, queue, consistency).
  7. Bottlenecks & trade-offs — where it breaks at scale, how you'd fix it, what you traded.
Senior signal: always state trade-offs ("I'd choose eventual consistency here to stay available, and make writes idempotent"). Naming the trade-off > naming the tech.

14 · Rapid-Fire Conceptual Q&A (40+)

Idempotent vs safe method?

Safe = no side effects (GET); idempotent = same result if repeated (GET/PUT/DELETE).

Why idempotency keys?

So a retried POST (after a network blip) doesn't create/charge twice.

Cache-aside vs write-through?

Cache-aside = populate on miss; write-through = write cache+DB together (consistent, slower).

Hardest cache problem?

Invalidation — keeping cache fresh; use TTL, versioned keys, or event-based invalidation.

Cache stampede?

Many simultaneous misses hammer the DB; fix with locks/coalescing/staggered TTLs.

L4 vs L7 load balancer?

L4 routes by TCP (fast); L7 is HTTP-aware (route by path/header, TLS termination).

Why stateless services?

Any instance can serve any request → easy horizontal scaling and failover.

Vertical vs horizontal scaling?

Bigger box vs more boxes; horizontal scales further but needs statelessness.

CAP in one line?

Under a partition, choose consistency or availability, not both.

Strong vs eventual consistency?

Always-latest (slower) vs converges-over-time (faster, may be stale).

At-least-once vs exactly-once?

At-least-once may duplicate → make processing idempotent; true exactly-once delivery is impractical.

Queue vs pub/sub?

Queue = one consumer per message; pub/sub = every subscriber gets it.

What's a DLQ?

Dead-letter queue for messages that repeatedly fail, so they don't block the main queue.

How ensure message ordering?

Partition by key / FIFO groups; global ordering is expensive.

2PC vs Saga?

2PC = blocking distributed commit; Saga = local txns + compensations (preferred in microservices).

Circuit breaker?

After repeated failures, fail fast for a while to stop cascading failures, then test recovery.

Retry best practice?

Exponential backoff + jitter, capped attempts, only on transient errors, idempotent ops.

Bulkhead?

Isolate resource pools so one failing dependency can't exhaust everything.

Monolith vs microservices — when split?

Start monolith; split when team/scale/deploy independence demands it.

How do microservices share data?

Each owns its DB; sync via events/saga — no shared database.

API gateway does what?

Single entry: routing, auth, rate limiting, aggregation.

gRPC vs REST?

gRPC = binary/protobuf over HTTP2, fast, typed, streaming (service-to-service); REST = simple, cacheable, browser-friendly.

When GraphQL?

Clients need flexible field selection / avoid over-fetching; downside: caching & rate-limiting harder.

HTTP/2 benefit?

Multiplexing many streams over one connection + header compression.

TCP vs UDP?

Reliable/ordered vs fast/unreliable.

What does TLS give you?

Confidentiality, integrity, server authentication.

Session vs JWT?

Server state + easy revoke vs stateless + scales, hard to revoke.

OAuth vs OIDC?

OAuth = authorization (access); OIDC adds identity (who the user is).

RBAC vs ABAC?

Role-based vs attribute/policy-based access.

Rate limiting algorithms?

Token bucket, leaky bucket, fixed/sliding window.

p99 vs average latency?

p99 exposes tail latency that averages hide — what users actually feel.

Latency vs throughput?

Time per request vs requests per second.

Why connection pooling?

Reuse expensive connections instead of opening one per request.

Sharding vs replication?

Sharding splits data (scale writes); replication copies data (scale reads + HA).

Replication lag risk?

Reading a replica may return stale data (no read-your-writes).

Three pillars of observability?

Logs, metrics, traces.

Correlation ID?

An ID propagated across services to trace one request end-to-end.

SLI/SLO/SLA?

Indicator / objective / agreement; error budget = allowed unreliability.

CSRF vs XSS?

CSRF = forged request using your cookie; XSS = injecting script into a page.

Where do secrets go?

Secret manager / env vars, never in code; rotate them.

Event sourcing?

Store state as an append-only log of events (replayable, auditable).

Strangler pattern?

Incrementally replace a legacy system by routing pieces to new services.

15 · Deep-Dive Follow-ups (layer 2 & 3)

The chains interviewers push after your first architecture answer.

Caching → ↳ How do you keep cache and DB consistent?

There's no perfect answer — common pattern is cache-aside with invalidate-on-write (write DB, then delete the cache key). Deleting (not updating) avoids races; TTL is the safety net. Accept a small window of staleness.

↳↳ How do you prevent a cache stampede?

Request coalescing / a per-key mutex (only one caller refills, others wait), staggered/jittered TTLs, or probabilistic early expiration (refresh slightly before expiry).

CAP → ↳ Give an AP and a CP system.

AP: DynamoDB/Cassandra (stay available, eventual). CP: a system that refuses writes during a partition to stay consistent (e.g., a strongly-consistent store / ZooKeeper-backed). Most real systems are tunable per-operation.

↳↳ What's PACELC?

Extends CAP: during a Partition choose A or C; Else (normal operation) choose Latency or Consistency. Captures the everyday latency-vs-consistency trade-off CAP ignores.

↳ How do replicas reconcile conflicts under eventual consistency?

Last-write-wins (timestamps), vector clocks, or CRDTs depending on the system.

Idempotency → ↳ How do you actually implement an idempotent consumer?

Store processed message/idempotency keys in a dedupe table (with TTL); on each message, check-and-set atomically — if seen, skip. This turns at-least-once delivery into effectively-once processing.

↳↳ The "dual write" problem & the outbox pattern?

Writing to DB and publishing an event as two separate steps can partially fail. Outbox: write the event into an outbox table in the same DB transaction, then a relay publishes it — guarantees the event iff the data was committed.

Load balancing → ↳ Sticky sessions — good or bad?

They pin a user to one server (needed if state is in-memory) but hurt scaling/failover. Better: make services stateless (state in Redis) so any server handles any request.

↳ What's consistent hashing and why?

Maps keys to nodes on a ring so adding/removing a node only remaps a small fraction of keys (not all). Used for cache/shard distribution to avoid mass rehashing.

Rate limiting → ↳ token bucket vs sliding window?

Token bucket allows bursts up to bucket size then steady refill. Fixed window is simple but allows 2x bursts at boundaries. Sliding-window counter smooths that out. Choose by whether bursts are acceptable.

↳↳ How do you rate-limit across many servers?

Centralize the counter in Redis (atomic INCR + expiry, or a Lua script for token bucket) so all instances share one limit.

Microservices → ↳ Saga: orchestration vs choreography?

Orchestration = a central coordinator tells each service what to do (easier to reason/monitor, single point). Choreography = services react to each other's events (decoupled, but flow is harder to trace). Pick by complexity/visibility needs.

↳ How do you debug a request across 10 services?

Distributed tracing — propagate a trace/correlation ID through every call (OpenTelemetry), so you can see the full span timeline in Jaeger/Dynatrace.

If short on time, master: caching (strategies + invalidation) · load balancing & horizontal scaling · CAP + consistency · queues + delivery guarantees + idempotency · circuit breaker/retries/timeouts · the system-design approach. These recur in almost every senior backend conversation.
