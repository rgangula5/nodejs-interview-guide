1 · SOLID Principles

Five principles for maintainable OO design. Know the letter, the one-line meaning, and a concrete violation→fix.

S — Single Responsibility

A class/module should have one reason to change — one job. A UserService that also formats emails and writes files has three reasons to change; split them.

↳ Isn't "one responsibility" vague? How do you decide?

Frame it as "one reason to change / one actor." If two stakeholders (e.g., DBA and marketing) would request changes to the same class, it has two responsibilities.

O — Open/Closed

Open for extension, closed for modification. Add new behavior via new code (new subclass/strategy), not by editing tested existing code.

↳ How do you achieve it concretely?

Program to interfaces/abstractions + polymorphism or Strategy pattern. e.g., a PaymentProcessor interface; add StripeProcessor without touching existing ones. A switch you keep editing per new type is an OCP smell.

L — Liskov Substitution

Subtypes must be substitutable for their base type without breaking behavior. The classic violation: Square extends Rectangle where setting width also changes height, breaking code that expects Rectangle semantics.

↳ Give the rule of thumb.

A subclass shouldn't strengthen preconditions or weaken postconditions, or throw on methods the base supports. "Is-a" in code must hold behaviorally, not just structurally.

I — Interface Segregation

Clients shouldn't depend on methods they don't use. Prefer small, focused interfaces over one fat interface. A Machine interface forcing a simple printer to implement scan()/fax() is a violation.

↳ How does this relate to SRP?

SRP is about a class's responsibilities; ISP is about not forcing clients to depend on a bloated contract. Both push toward small, cohesive units.

D — Dependency Inversion

High-level modules shouldn't depend on low-level details; both depend on abstractions. Depend on an interface (Logger), not a concrete (FileLogger) — inject the concrete in.

↳ Difference between Dependency Inversion and Dependency Injection?

Inversion (DIP) is the principle (depend on abstractions). Injection (DI) is a technique to achieve it (pass dependencies in via constructor/params instead of creating them inside). DI is one way to satisfy DIP.

Say this: "SOLID keeps code changeable — SRP/ISP keep units small, OCP/DIP let me add features without editing tested code, LSP keeps polymorphism safe."

2 · Creational Patterns

Singleton

One shared instance, global access point (config, DB pool, logger).

let instance;
export function getDb() { return instance ??= createPool(); }

↳ Why do people call Singleton an anti-pattern?

Global mutable state → hidden coupling, hard to test/mock, concurrency issues. Prefer passing the single instance via DI so it's explicit and swappable. In Node, a module is already a cached singleton — often you don't need the pattern at all.

Factory Method / Factory

Encapsulate object creation behind a function/method so callers don't new concretes directly.

function makeLogger(kind) {
  return kind === 'file' ? new FileLogger() : new ConsoleLogger();
}

↳ Factory vs Abstract Factory?

Factory creates one product; Abstract Factory creates families of related products behind one interface (e.g., a UI factory producing matching Button + Checkbox for a theme).

Builder

Construct a complex object step-by-step; avoids telescoping constructors.

new QueryBuilder().select('*').from('users').where('id=1').build();

↳ Builder vs Factory?

Factory decides which object; Builder assembles one complex object incrementally with many optional parts.

Prototype

Create new objects by cloning an existing one (when construction is expensive). In JS this maps to Object.create/structuredClone.

3 · Structural Patterns

Adapter

Wrap an incompatible interface so it matches what your code expects (e.g., adapt a 3rd-party SDK to your PaymentProcessor interface).

↳ Adapter vs Facade?

Adapter converts one interface to another (compatibility). Facade simplifies a complex subsystem behind one easy interface.

Decorator

Add behavior to an object by wrapping it, without changing its class (composition over inheritance). Node middleware and stream wrapping are decorator-flavored.

const timed = (fn) => (...a) => { const s=Date.now(); const r=fn(...a); log(Date.now()-s); return r; };

↳ Decorator vs inheritance for adding behavior?

Decorator stacks behaviors at runtime and avoids subclass explosion; inheritance is static and can violate OCP when combinations multiply.

Facade

A simple front over a complex subsystem (e.g., one OrderService.place() hiding inventory, payment, shipping calls).

Proxy

A stand-in controlling access to another object — for lazy loading, caching, access control, or logging. JS has a built-in Proxy.

↳ Proxy vs Decorator?

Both wrap. Decorator adds behavior; Proxy controls access (same interface, may deny/defer/cache).

Composite

Treat individual objects and groups uniformly via a tree (e.g., files & folders both implement size()).

4 · Behavioral Patterns

Observer (Pub/Sub)

Subject notifies subscribers of changes. Node's EventEmitter is Observer. Decouples producers from consumers.

↳ Observer vs Pub/Sub — same thing?

Similar; classic Observer has the subject directly hold its observers. Pub/Sub usually adds a broker/event bus between them, so publishers and subscribers don't know each other at all (looser coupling).

Strategy

Encapsulate interchangeable algorithms behind one interface; swap at runtime. The go-to for Open/Closed (add a new strategy, don't edit a switch).

const sorters = { quick: quickSort, merge: mergeSort };
function sort(data, strategy) { return sorters[strategy](data); }

Command

Encapsulate a request as an object (with execute()) — enables queues, undo/redo, logging of operations.

Chain of Responsibility

Pass a request along a chain of handlers until one handles it. Express middleware is exactly this.

↳ Which real Node thing is Chain of Responsibility?

The middleware pipeline — each handler processes or calls next() to pass the request along.

Iterator

Sequential access without exposing internals. JS iterables/generators (for...of, Symbol.iterator) are built-in Iterator.

State & Template Method

State — object changes behavior as its internal state changes (like a state machine). Template Method — base class defines the algorithm skeleton, subclasses fill in steps.

5 · Backend / Node Patterns

  • Dependency Injection — pass deps (db, logger, config) into a class/function instead of creating them inside → testable, swappable (satisfies DIP). NestJS is built around a DI container.
  • Repository — abstract data access behind an interface (UserRepo.findById) so business logic doesn't know the data source; swap DB or mock in tests.
  • Middleware / Pipeline — Chain of Responsibility for cross-cutting concerns (auth, logging, validation).
  • Module pattern — encapsulate private state, expose a public API (classic pre-ESM; still conceptually relevant).
  • Circuit Breaker — stop calling a failing dependency after N failures; fail fast, then test recovery (resilience). See Backend Concepts page.
  • Saga — manage a distributed transaction as local steps + compensations.

↳ How does DI help testing?

You inject a mock/stub instead of the real dependency, so you can unit-test logic in isolation without a real DB/network.

6 · Anti-patterns (know a few)

  • God object — one class doing everything (violates SRP).
  • Spaghetti / tight coupling — no abstractions; a change ripples everywhere.
  • Callback hell — deeply nested callbacks (fix with Promises/async).
  • Magic numbers/strings — unexplained literals; use named constants.
  • Premature optimization / over-engineering — patterns for their own sake.
  • Singleton overuse — hidden global state.

Small focused interfaces; don't force unused methods.

Principle (depend on abstractions) vs technique (inject dependencies).

One shared instance; often an anti-pattern (global state).
