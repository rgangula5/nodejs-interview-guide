1 · Node.js Fundamentals & Architecture

What is Node.js?

Node.js is a runtime that lets you run JavaScript outside the browser, on the server. It's built on Chrome's V8 engine (compiles JS to machine code) plus libuv (a C library that provides the event loop and asynchronous, non-blocking I/O). Node is single-threaded for your JS code, event-driven, and uses non-blocking I/O, which makes it great for I/O-heavy, high-concurrency workloads (APIs, real-time services) and poor for CPU-heavy work.

Why is Node good for I/O but bad for CPU-bound tasks?

I/O (network, file, timers) is delegated to libuv / the OS and runs asynchronously, so one thread can juggle thousands of connections. But a CPU-heavy task (e.g., image processing, big loops) runs on the single main thread and blocks the event loop — every other request stalls. Fix: offload to worker_threads, child_process, a queue, or a separate service.

Single-threaded — but Node uses threads. Explain.

Your JavaScript runs on one thread. But libuv keeps a thread pool (default 4, set via UV_THREADPOOL_SIZE) for certain operations that can't be done async at the OS level — file system I/O, DNS lookups (dns.lookup), and CPU-bound crypto (crypto.pbkdf2, zlib). Network I/O uses the OS's async facilities (epoll/kqueue), not the thread pool.

Say this: "JS is single-threaded; I/O is offloaded to libuv, so Node scales I/O concurrency cheaply. The moment you do CPU work on the main thread you block everything — so I move that to a worker thread or a queue."

2 · The Event Loop (the #1 asked topic)

The event loop is what lets single-threaded Node do non-blocking I/O. When an async operation finishes, its callback is queued and the loop runs it when the stack is clear. libuv runs the loop in phases, in this order, repeating each tick:

  • Timers — callbacks from setTimeout / setInterval whose time is due.
  • Pending callbacks — some system-level callbacks (e.g., TCP errors).
  • Poll — retrieves new I/O events; executes I/O callbacks (most of your work happens here). Blocks here if nothing else to do.
  • Check — setImmediate callbacks.
  • Close — close callbacks (e.g., socket.on('close')).

Microtasks vs macrotasks — the key nuance

Between every phase (and after each callback), Node drains two microtask queues, in this order:

  • process.nextTick() queue — highest priority, runs first.
  • Promise (microtask) queue — .then/.catch/finally, await continuations.

Macrotasks = timers, setImmediate, I/O callbacks (the phases above). Microtasks always drain fully before moving on.

Predict the output

console.log('1 sync');
setTimeout(() => console.log('2 timeout'), 0);
setImmediate(() => console.log('3 immediate'));
Promise.resolve().then(() => console.log('4 promise'));
process.nextTick(() => console.log('5 nextTick'));
console.log('6 sync');

// Output:
// 1 sync
// 6 sync
// 5 nextTick      <- microtask, before promises
// 4 promise       <- microtask
// 2 timeout  /  3 immediate  (order between these two can vary)

setTimeout(fn,0) vs setImmediate vs process.nextTick?

  • process.nextTick — runs before the event loop continues, after the current operation. Can starve the loop if used recursively.
  • Promise .then — microtask, right after nextTick.
  • setImmediate — runs in the check phase (after poll).
  • setTimeout(fn,0) — runs in the timers phase; minimum ~1ms, not truly 0.
Say this: "Microtasks — nextTick then Promises — drain completely between event-loop phases. So a Promise callback always runs before a setTimeout, even a 0ms one."

3 · Async: Callbacks, Promises, async/await

Error-first callbacks & callback hell

fs.readFile('a.txt', (err, data) => {
  if (err) return handle(err);   // error-first convention
  // nesting more callbacks here => "callback hell"
});

Promises & combinators

  • Promise.all([...]) — waits for all; rejects fast if any one rejects.
  • Promise.allSettled([...]) — waits for all; never rejects; returns {status,value|reason}.
  • Promise.race([...]) — settles with the first to settle (resolve or reject).
  • Promise.any([...]) — first to fulfill; rejects only if all reject (AggregateError).

async/await — sequential vs parallel (common trap)

// SLOW - sequential, ~2x time
const a = await getA();
const b = await getB();

// FAST - parallel, both start together
const [a, b] = await Promise.all([getA(), getB()]);

How do you handle errors in async/await?

try {
  const data = await risky();
} catch (err) {
  // handles both sync throws and rejected promises
}
// In Express, wrap async handlers so rejections reach error middleware:
const wrap = fn => (req,res,next) => Promise.resolve(fn(req,res,next)).catch(next);
Gotcha: forEach does NOT await. Use for...of with await for sequential, or Promise.all(arr.map(...)) for parallel.

4 · Modules (CommonJS vs ESM)

  • CommonJS (require/module.exports) — synchronous, default in Node historically. require is cached after first load (module is a singleton).
  • ES Modules (import/export) — standard, async-friendly, static analysis / tree-shaking. Enable via "type":"module" in package.json or .mjs.
  • Differences: ESM imports are hoisted & static (can't conditionally import at top level; use dynamic import()); __dirname/__filename not available in ESM (use import.meta.url); this is undefined at module top in ESM vs module.exports in CJS.

Module wrapper: Node wraps each file in a function giving you exports, require, module, __filename, __dirname — that's why these "globals" exist per-file.

5 · Streams & Buffers

Streams process data in chunks instead of loading it all into memory — essential for large files/payloads.

  • Readable (fs read, HTTP request), Writable (fs write, HTTP response), Duplex (both, e.g., TCP socket), Transform (modify while passing, e.g., zlib/gzip).
  • pipe() connects readable → writable and handles backpressure automatically.
fs.createReadStream('big.log')
  .pipe(zlib.createGzip())
  .pipe(fs.createWriteStream('big.log.gz'));

What is backpressure?

When a readable produces data faster than the writable can consume it. pipe() (and stream.pipeline()) manage it by pausing the source until the destination drains, preventing memory blow-up. pipeline() is preferred — it also forwards errors and cleans up.

Buffer?

A fixed-length chunk of binary data outside the V8 heap. Used for raw bytes — file contents, network packets, crypto. Buffer.from('hi'), buf.toString('utf8').

6 · EventEmitter

Node's pub/sub building block; many core objects (streams, HTTP server) are EventEmitters.

const { EventEmitter } = require('events');
const bus = new EventEmitter();
bus.on('order', (id) => console.log('got', id));  // subscribe
bus.emit('order', 42);                             // publish
// once() = one-time; removeListener() to unsubscribe.
Emitters are synchronous — listeners run in registration order, on the same tick. A thrown error in a listener with no 'error' handler crashes the process.

7 · Error Handling

  • Operational errors (expected: bad input, network fail) — handle & respond gracefully.
  • Programmer errors (bugs: undefined access) — let it crash, fix the code; don't try to recover.
// last-resort safety nets (log + exit; don't keep running in bad state)
process.on('uncaughtException', err => { log(err); process.exit(1); });
process.on('unhandledRejection', err => { log(err); process.exit(1); });

Central error handling in Express

// Error-handling middleware has FOUR args (err first):
app.use((err, req, res, next) => {
  const status = err.status || 500;
  res.status(status).json({ error: err.message });
});
Say this: "I separate operational from programmer errors, funnel everything to one error-handling middleware, and use last-resort uncaughtException/unhandledRejection handlers that log and exit so a process manager restarts a clean instance."

8 · HTTP & the http Module

const http = require('http');
const server = http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({ ok: true }));
});
server.listen(3000);

req is a Readable stream, res is a Writable stream. Express is a thin, ergonomic layer on top of this: routing + middleware + helpers (res.json, req.params).

9 · Express & MIDDLEWARE (deep dive)

What is middleware?

A function that sits in the request→response pipeline with access to the request (req), the response (res), and the next function. It can: run code, modify req/res, end the response, or call next() to pass control to the next middleware. Express is essentially "a stack of middleware executed in order."

function logger(req, res, next) {
  req.startTime = Date.now();        // modify req
  console.log(req.method, req.url);  // run code
  next();                            // pass control on
}
app.use(logger);

The middleware signature & the role of next()

  • (req, res, next) — normal middleware.
  • (err, req, res, next) — error middleware (4 args; Express detects the arity).
  • next() — go to the next middleware.
  • next('route') — skip remaining middleware of the current route, jump to the next matching route.
  • next(err) — skip all normal middleware and jump straight to error-handling middleware.
Most common bug: forgetting next() (or a response). The request just hangs forever. Every middleware must either end the response or call next().

Order matters — explain

Middleware runs top-to-bottom in the order registered. So express.json() must come before routes that read req.body; auth middleware before protected routes; the 404 handler after all routes; the error handler last.

app.use(express.json());        // 1. parse body
app.use(logger);                // 2. log
app.use('/api', authMiddleware);// 3. protect /api
app.use('/api/users', usersRouter); // 4. routes
app.use((req,res) => res.status(404).json({error:'Not found'})); // 5. 404
app.use(errorHandler);          // 6. errors (last, 4 args)

Types of middleware (name them)

  • Application-level — app.use(fn) / app.get(path, fn).
  • Router-level — bound to an express.Router() instance.
  • Error-handling — the 4-arg one.
  • Built-in — express.json(), express.urlencoded(), express.static().
  • Third-party — cors, helmet, morgan, compression, express-rate-limit, cookie-parser.

Route-specific vs global middleware

// global
app.use(logger);
// single route, multiple middleware in a chain:
app.get('/admin', authMiddleware, requireAdmin, (req,res) => res.send('ok'));

Write an auth middleware (very common ask)

function auth(req, res, next) {
  const token = req.headers.authorization?.split(' ')[1];
  if (!token) return res.status(401).json({ error: 'No token' });
  try {
    req.user = verifyToken(token);   // attach to req for downstream
    next();
  } catch {
    return res.status(401).json({ error: 'Invalid token' });
  }
}

Write a middleware factory (parameterized middleware)

// returns a middleware — lets you configure per-route
function requireRole(role) {
  return (req, res, next) => {
    if (req.user?.role !== role) return res.status(403).json({error:'Forbidden'});
    next();
  };
}
app.delete('/users/:id', auth, requireRole('admin'), handler);

How do you handle async errors in middleware?

// async middleware must forward rejections to next():
const asyncH = fn => (req,res,next) => Promise.resolve(fn(req,res,next)).catch(next);
app.get('/x', asyncH(async (req,res) => {
  const data = await service();   // if this throws, next(err) fires
  res.json(data);
}));
// (Express 5 auto-forwards async rejections; Express 4 needs this wrapper.)

The "onion" / pipeline model

Requests flow down the middleware stack to the route handler, then the response flows back up. Middleware can act before and after next() (e.g., start a timer before, log duration after):

app.use(async (req, res, next) => {
  const start = Date.now();
  await next();                         // let downstream run
  console.log('took', Date.now() - start, 'ms'); // runs on the way back
});

Express vs Koa middleware (sometimes asked)

Express uses callback-style next(). Koa (by the same team) uses async/await middleware with a cleaner onion model (await next()) and a single ctx object instead of req/res. Concept is the same; Koa is lighter and modern-async-first.

One-liner to nail it: "Middleware is a function with (req,res,next) that runs in registered order; it either responds or calls next(). Error middleware takes four args and everything funnels to it. Order is everything — parsers first, auth before protected routes, error handler last."

10 · Building REST APIs

  • REST principles: resources (nouns) as URLs, HTTP verbs for actions (GET/POST/PUT/PATCH/DELETE), stateless, standard status codes.
  • Status codes: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable, 429 Too Many Requests, 500 Server Error.
  • Idempotency: GET/PUT/DELETE should be safe to retry with the same result; POST is not idempotent (use idempotency keys for payments).
  • Versioning: /api/v1/... or headers.
  • Pagination: ?limit=&offset= or cursor-based.
  • Validation: validate input at the edge (middleware) — reject bad requests with 400/422 before business logic. (You use Zod — mention schema validation as middleware.)

11 · Authentication & Security

JWT vs sessions

  • Sessions — server stores session state, client holds a session-id cookie. Stateful; easy to revoke; needs shared store to scale.
  • JWT — signed token (header.payload.signature) holding claims; stateless, server just verifies the signature. Scales well; harder to revoke (use short expiry + refresh tokens). Never put secrets in the payload — it's base64, not encrypted.

Refresh tokens

Short-lived access token (~15 min) + long-lived refresh token (stored securely, e.g., httpOnly cookie). When the access token expires, exchange the refresh token for a new one — limits damage if an access token leaks.

Security checklist (say several)

  • helmet — sets secure HTTP headers.
  • CORS — restrict allowed origins.
  • Rate limiting — express-rate-limit to stop brute force/DoS.
  • Input validation & sanitization — prevent injection.
  • bcrypt/argon2 — hash passwords (never store plaintext).
  • Secrets in env/secret manager, never in code.
  • HTTPS, secure/httpOnly cookies, CSRF protection for cookie-based auth.
  • Keep deps patched (npm audit).

12 · Performance, Scaling, cluster & worker_threads

  • cluster — forks multiple Node processes (one per CPU core) sharing a port; the OS/master load-balances connections. Scales across cores since a single Node process uses one core for JS. (PM2 does this for you.)
  • worker_threads — real threads within one process, sharing memory (via SharedArrayBuffer). Best for CPU-bound work without blocking the main loop.
  • child_process — spawn separate programs/scripts (spawn, exec, fork).

cluster vs worker_threads?

cluster = multiple processes (isolated memory) for scaling I/O concurrency across cores. worker_threads = threads (shared memory) for CPU-bound computation. Rule of thumb: scale a web server with cluster/PM2; offload heavy computation to worker_threads.

Other performance levers

  • Caching (in-memory / Redis), compression middleware (gzip), keep-alive.
  • Avoid blocking the loop (no sync fs/crypto on the hot path).
  • Stream large responses instead of buffering.
  • Use a process manager (PM2) for clustering + auto-restart; put Nginx/ALB in front.

14 · Node Internals (libuv, memory, GC)

  • libuv — C library providing the event loop, thread pool, and async I/O abstractions across OSes.
  • V8 memory — young (new) space + old space (heap). GC is generational (Scavenge for young, Mark-Sweep-Compact for old).
  • Memory leaks — common causes: growing global arrays/maps, unremoved event listeners, closures holding references, caches without eviction. Diagnose with --inspect + Chrome DevTools heap snapshots, process.memoryUsage().
  • Default heap ~1.5–2GB; raise with --max-old-space-size.

16 · Rapid-Fire Q&A (50+)

Is Node single or multi-threaded?

JS runs single-threaded; libuv adds a thread pool for some I/O. So "single-threaded event loop with a background thread pool."

What's the event loop in one sentence?

The mechanism that lets single-threaded Node handle many concurrent operations by queuing callbacks and running them when the call stack is empty.

nextTick vs setImmediate?

nextTick runs before the loop continues (highest priority microtask); setImmediate runs in the check phase after poll.

Promise vs setTimeout(0)?

Promise callback (microtask) always runs before setTimeout (macrotask).

Callback hell fix?

Promises / async-await / modularizing functions.

Promise.all vs allSettled?

all rejects on first failure; allSettled waits for all and never rejects.

What is middleware?

A function (req,res,next) in the request pipeline that can modify req/res, end the response, or pass control via next().

How many args does error middleware take?

Four: (err, req, res, next).

What does next() do? next(err)?

next() → next middleware; next(err) → jumps to error-handling middleware.

What happens if you forget next()?

The request hangs — no response, no next middleware.

Order of middleware — why care?

They run in registration order; parsers/auth must precede handlers, error handler is last.

express.json() does what?

Built-in middleware that parses JSON request bodies into req.body.

app.use vs app.get?

use = all methods/any path prefix; get = GET on a specific path.

Router-level middleware?

Middleware attached to an express.Router() instance, mounted at a base path.

How to make config-able middleware?

A factory function that returns a middleware.

Streams — why?

Process data in chunks to avoid loading everything in memory; handle large files/payloads.

Backpressure?

Producer faster than consumer; pipe()/pipeline() pause the source to avoid memory blowup.

Buffer?

Fixed-length binary data outside the V8 heap.

EventEmitter?

Pub/sub: on()/emit(); synchronous; core to streams & servers.

CommonJS vs ESM?

require (sync, cached) vs import/export (static, async-friendly, tree-shakeable).

Is require cached?

Yes — a module loads once and is reused (singleton).

__dirname in ESM?

Not available; derive from import.meta.url.

uncaughtException — should you keep running?

No; log and exit, let a process manager restart clean.

Operational vs programmer error?

Expected runtime issues to handle vs bugs to fix (and let crash).

JWT vs session?

Stateless signed token vs server-stored state; JWT scales, sessions revoke easily.

Is JWT encrypted?

No — it's signed & base64-encoded; anyone can read the payload. Don't put secrets in it.

How to revoke a JWT?

Short expiry + refresh tokens, or a denylist/rotation.

cluster vs worker_threads?

Processes for I/O scaling across cores vs threads (shared memory) for CPU work.

How to not block the event loop?

Avoid sync CPU work; offload to worker_threads/queues; use async APIs.

UV_THREADPOOL_SIZE?

Env var controlling libuv's thread pool size (default 4).

middleware for logging request duration?

Record start time, await next(), log Date.now()-start on the way back.

helmet / cors / rate-limit?

Security headers / origin control / throttle requests — all middleware.

How to hash passwords?

bcrypt or argon2 with a salt; never plaintext or fast hashes.

Idempotent methods?

GET, PUT, DELETE (safe to retry); POST is not.

Status for validation failure?

400 (bad request) or 422 (unprocessable entity).

supertest is for?

Integration-testing HTTP endpoints against the Express app.

package-lock.json?

Locks exact dependency versions for reproducible installs (npm ci).

^ vs ~ in semver?

^ allows minor+patch updates; ~ allows patch only.

process.nextTick starvation?

Recursive nextTick can starve the event loop (I/O never runs). Prefer setImmediate for "run soon."

How does Express relate to http?

It's a framework layer over the core http module adding routing + middleware.

Global objects in Node?

process, Buffer, __dirname/__filename (CJS), setTimeout/setInterval/setImmediate, console.

What is process.env?

Environment variables object — used for configuration/secrets.

Graceful shutdown?

On SIGTERM, stop accepting new connections, finish in-flight requests, close resources, then exit.

Difference: exec vs spawn?

exec buffers output (small results), spawn streams it (large/continuous output).

17 · How to Answer ANY Node Question (framework)

  1. One-sentence definition first. ("Middleware is a function with req/res/next in the request pipeline.")
  2. Then the why / when. ("You use it for cross-cutting concerns — auth, logging, validation.")
  3. Then a tiny concrete example (name a real one you built — your Lambda authorizer, request validation with Zod, your CI/logging middleware).
  4. Mention a trade-off or gotcha — shows senior depth (order matters / forgetting next() hangs the request / blocking the loop).
Senior signal: tie answers to real systems you built — event-driven services, a JWT authorizer, idempotent handlers, structured error middleware. Concrete beats textbook.

Focus areas if short on time: Event loop, Middleware & next(), async/await + Promise.all, error handling, JWT, cluster vs worker_threads. Those five cover ~80% of backend Node interviews.
